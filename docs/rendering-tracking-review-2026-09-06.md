# 虚拟窗口：渲染与追踪改进记录

日期：2026-09-06。范围：主项目代码、同级九个资料／实现目录、相关作者原始资料。只修改主项目，没有重写其他引擎，也没有部署到公网。

## 结论

保留 **React / Three.js / WebGL2 + Python / MediaPipe / FastAPI / WebSocket**，增加 **Spark 2.1.0** 作为可选高斯渲染层。已有网格负责箱体、可编辑物件、灯光与阴影；高斯负责带真实拍摄外观的扫描内容。离线训练和素材编辑与实时追踪分离。

“场景看起来真实”“透视几何正确”“观看者位置准确”“运动稳定”是四个不同问题。高斯泼溅主要改善第一项，不能替代眼睛定位、相机标定或时序处理。Spark 原生加入 Three.js 场景并使用同一个相机，符合当前项目的接入边界。[Spark 官方概览](https://sparkjs.dev/docs/overview/)

| `splat-main` | 精简 WebGL 查看器、工作线程排序 | 适合学习透明合成与排序，不优先接入：场景集成、格式与扩展能力不如 Spark，README 本身也推荐 Spark；其简化 SH 策略有外观取舍。 |

| `awesome-3D-gaussian-splatting-main` | 论文索引 | 用来寻找抗锯齿、压缩、几何恢复等方向，不是可运行渲染引擎。 |

## 已完成的代码改动

### 1. 离轴投影与显示比例

将投影抽到 `web/lib/window-projection.ts`。窗口固定在世界坐标 z=0，相机不使用 lookAt 指向物件。使用 Kooima 的 generalized perspective construction（[论文](https://csc.lsu.edu/~kooima/pdfs/gen-perspective.pdf)）从屏幕左下、右下、左上三个角和观察点构造左右上下不对称视锥；屏幕基向量必须正交，避免把一个剪切平面误当作矩形而产生“扭转”。需要保护近平面时，同时修改相机位置和投影距离，避免两者不一致。

同步 `fov`、`aspect` 和逆投影矩阵。原先虽然写入了离轴矩阵，`camera.fov=45`、`aspect=16/9` 仍未更新；读取这些字段的下游像素尺度／LOD 算法可能与实际投影不符。Spark 的顶点着色器使用完整投影矩阵定位中心，并从矩阵取焦距计算二维协方差；此路径可以保留离轴投影。此后不能再调用普通 `updateProjectionMatrix()` 覆盖偏移。

网页区域比例现在跟随展示箱宽高；全屏也等比留边，不再强制拉伸到整个屏幕。远平面至少覆盖屏幕后方箱体。实测模式的眼睛移动现在以中性眼为锚点做仿射米制映射，x/y/z 使用同一个米到场景单位比例，不再用绝对 z 比例扭曲横向和纵深。

实机检查还发现鼠标模式下工具栏点击会被父层拖拽的指针捕获拦截；已隔离工具栏事件，使切回人脸追踪、复位和全屏按钮正常响应。

窗口现在统一采用按实测尺寸投影：输入实际**渲染矩形宽度**及校准时眼屏距离，采用统一米到场景单位比例；不再分别猜 XY 和 Z 增益。窗口只是投影视口，单模型和完整场景共享同一空间，模型可用带符号深度凸出窗外且不会被自动缩放。该方案仍假设摄像头与屏幕方向基本一致；完整场景可通过 `web/lib/window-anchor.ts` 提供的锚点 API 指定窗户在场景中的位置和方向，摄像头外参尚未自动标定。

### 2. 追踪时序、异常值与校准

`src/face_tracker/stabilization.py` 对有效位置做时间连续性关联。初始化选最大脸，后续优先靠近前次有效位置的候选；检测返回顺序改变不直接换人。它是短时几何关联，**不做人脸身份识别**，两张脸交叉时仍可能关联错误。

拒绝非有限坐标、异常深度和超出速度门限的跳点；短暂遮挡保留滤波状态，超过 0.75 秒再重新捕获并更新 track_id。速度门限是交互启发式，快速大幅移动可能被暂时拒绝，需要真实使用中继续调参。

滤波使用帧读取后的单调时间，不再使用推理结束时间；相机重连时检测时间也不从零重新开始。服务的 `captured_at_unix_ms` 现在记录读取完成时刻，并增加 `published_at_unix_ms`、`processing_ms`。这不是硬件曝光时间；驱动队列延迟尚未测量。断流后清空缓存，避免提供旧包。

前端 `web/lib/window-tracking.ts` 拒绝重复／乱序序列和非法坐标。校准需要至少 10 帧、至少 250 ms，取最近窗口中位数并要求位置稳定。新 track_id、重连、手动复位重新校准。

丢失判断只依据**最后有效样本**：250 ms 没有有效位置视为丢失，700 ms 后平滑回到中心。连续 tracking=false、静默连接、离线均不会无限保持旧视角；计时检查间隔 50 ms。没有为每个失败包重启复位定时器。

### 3. 降低渲染重复工作与双重平滑延迟

只在设置变化时更新材质、灯光和场景参数；只在像素比例改变时调用 `setPixelRatio`。本机 Three 源码中此方法会调用 `setSize`，原先每帧调用没有必要。箱体配置未改变时不重建几何。

静态阴影只在模型／灯光／箱体设置或内容可见性改变时刷新，使用当前的 PCFShadowMap。摄像头运动不需要重算固定灯光的阴影图。若后续增加物体动画，必须让动画触发阴影更新。

后端 One Euro beta 从 0.035 调为 4.0（输入单位米）；前端指数跟随速度从 11 调为 28，时间常数从约 91 ms 缩短到 36 ms。未默认开启位置预测，以免预测噪声或遮挡时过冲。

左上角显示活动渲染帧率和帧间隔 P95，便于观察卡顿；它不是 GPU 耗时或端到端延迟，后台暂停超过一秒不计入活动帧统计。

### 4. Spark 高斯入口

新增 `web/lib/gaussian-layer.ts`，只在点“高斯测试／导入高斯”时加载，普通网格路径不初始化 Spark。保持同一个 WebGLRenderer、深度缓冲和离轴相机；网格箱体与高斯共存。按相机 Z 深度排序，当前相机只平移、不旋转；这不等于逐像素精确透明排序。

支持本地 PLY / SPZ / SPLAT / KSPLAT 入口，文件不上传服务器。当前 PLY 要求二进制小端高斯属性，文本 PLY 会明确提示重新导出。文件大小暂限 128 MB，模型自动居中、等比缩放；可以沿用模型 XYZ／缩放控制，另有高斯坐标翻转开关。失败回退原网格；处理了并发切换和卸载时的过期加载结果。

内置 4,096 高斯测试环，另有 8 高斯二进制 PLY 解析夹具。**这些都不是照片重建素材，也不能代表百万高斯场景质量／性能**。这轮核查时没有找到现成的真实扫描高斯资产，未训练新场景。

初版关闭 LOD，避免小素材接入阶段混入非对称视锥的方向预算问题；同步 fov 只是必要条件，并不代表完成了离轴 LOD 验证。普通三角形仍需要抗锯齿，保留原 MSAA；后续纯高斯大场景应对比关闭 MSAA 与降低 DPR。[Spark 性能说明](https://sparkjs.dev/docs/performance/)

最终构建中的高斯按需模块约 4.94 MB、Three 模块约 0.53 MB（均为未压缩文件大小）。高斯首次加载／编译会产生短时停顿，按需加载只把这笔成本移出普通网格启动路径，并没有消除它；网络分发和大模型加载仍需另测。

## 哪些高斯原理值得继续引入

| 优先级 | 原理 | 本项目的收益与边界 |
|---|---|---|
| 高 | 各向异性高斯、协方差投影、SH 视角相关外观 | 当前 Spark 已提供基础渲染路径；配合真实多视图训练资产改善细节和材质观感。SH 不是动态灯光重照明。 |
| 高 | Mip-Splatting 的三维平滑与二维像素滤波 | 适合观察者前后移动时抑制闪烁／膨胀收缩；需要检查训练与显示端滤波约定，不能把单独加模糊称为完整 Mip-Splatting。 |
| 高 | 增密、剪枝、深度正则与曝光补偿 | 在离线训练中减少浮点、增强结构和曝光一致性；深度先验可能错误，必须做同场景对照，不能保证每个场景都提升。 |
| 中 | 层次 LOD、压缩、重要性剪枝 | 有大模型后再引入 RAD 分块／LOD，并验证偏轴可见区域；小文件体积不等于小显存占用。LightGaussian 的剪枝、SH 蒸馏是训练／压缩流程，不是浏览器开关。 |
| 中 | StopThePop 的更精细深度排序 | 若头部小幅移动造成透明层突然翻转，可研究其排序方法。普通中心深度排序有局限；尚未在本项目实现。 |
| 条件适用 | 2DGS / 表面重建 | 要准确物体表面、碰撞、可重打光的网格时更值得投入；新视图看起来像，不代表几何尺寸已准确。 |
| 低 | 4DGS、形变网络 | 适合真正动态的扫描内容；静态展示箱暂不需要，不能解决观看者追踪抖动。 |

原始依据：[3DGS](https://repo-sam.inria.fr/fungraph/3d-gaussian-splatting/)、[Mip-Splatting](https://niujinshuchong.github.io/mip-splatting/)、[LightGaussian](https://lightgaussian.github.io/)、[StopThePop 作者实现](https://github.com/r4dl/StopThePop)、[2DGS](https://surfsplatting.github.io/)。

## 验证结果与适用范围

- Python：19 项测试通过；前端：8 项测试通过；类型检查、lint、生产构建通过。
- 投影测试覆盖三种宽高比、三个观察位置以及相机近距离保护，窗口四角投影误差小于 1e-9 NDC。只证明数学实现，不证明真实屏幕／摄像头标定准确。
- 页面实际运行：网格、高斯测试环、本地二进制 PLY 成功显示；文本 PLY 失败时回退网格。真实 SPZ / KSPLAT 和大型扫描场景仍待有素材后验证。
- 实时摄像头 1280×720；一次 90 包本机采样约 30.90 Hz，100% 有效追踪；包间隔 P95 61.98 ms；处理均值 16.70 ms、P95 31.00 ms；读取完成到接收端均值 26.27 ms、P95 36 ms。短时样本受当前负载和人脸状态影响，不是优化前后受控实验，也不是长时间稳定性承诺。
- 依赖安装提示 11 项审计风险（其中 8 项 high）；本次没有执行强制大版本升级。对外发布前需单独验证依赖修复。Spark 与当前 Three 的组合还出现 Clock 弃用和着色器类型转换警告。开发热更新中发现排序 worker 尚未结束就被销毁，已将清理改为先移出场景、等待在途排序，再释放渲染资源（最长等待一秒）；极端 GPU 卡死和长期卸载压力测试尚未覆盖。

可复现的滤波模拟：30 Hz、静止交替 ±3 mm 噪声、随后 0.18 m/s 匀速移动。运行 `scripts/benchmark_tracking.py`：

| 指标 | 原 beta 0.035 | 新 beta 4.0 |
|---|---:|---:|
| 静止滤后标准差 | 0.335 mm | 0.352 mm |
| 匀速段平均跟随偏差 | 23.268 mm | 15.210 mm |
| 匀速等效滤波滞后 | 129.27 ms | 84.50 ms |

这是以极小静止噪声增加换取约 35% 的匀速滤波滞后降低。这里只比较后端滤波，不包含前端过渡、镜头、网络、显示器，也不代表真实定位精度。

## 使用与下一步

本次本机预览地址：http://127.0.0.1:3000/；跟踪服务：http://127.0.0.1:8765/api/v1/status。进程仅在本机监听。

```powershell
.\.venv\Scripts\face-tracker.exe serve --host 127.0.0.1 --port 8765
```

```powershell
cd web
npm run dev -- --host 127.0.0.1 --port 3000
```

验证：主目录 `.\.venv\Scripts\python.exe -m pytest -q`；web 目录 `npm test`、`npx tsc --noEmit`、`npm run lint`、`npm run build`。服务运行时可在 web 执行 `node tests/live-tracking.mjs`，只输出聚合指标，不保存人脸图片／坐标轨迹。

建议下一轮按顺序进行：

1. 实测渲染区域宽度和中性眼屏距离，确认水平移动方向；完成相机内参、镜头畸变及摄像头相对屏幕外参标定。当前估距仍依赖假定瞳距和水平 FOV；头部偏转会造成深度偏差。
2. 在受控轨迹上评估 Face Landmarker 的多关键点／姿态解算或深度相机，减少“转头误判为前后移动”；不要只继续叠加平滑。
3. 录制同一段位置输入重放，比较静止抖动、运动滞后、遮挡 0.2/1/3 秒、多人交叉、摄像头断连。若测到采集队列积压，再改为独立采集线程与单槽最新帧消费；**本次仍为串行采集／推理**。
4. 准备一套环绕拍摄且曝光稳定的素材，离线训练并经 SuperSplat 清理；在目标分辨率和眼睛活动范围内对比网格／高斯、SH、抗锯齿、DPR，最后才引入大场景 LOD。
